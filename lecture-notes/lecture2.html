Part 2 · Agent design patterns

The autonomy spectrum

Agents use tools to act on a user's request. Software can define the steps, or the model can choose them. People call systems anywhere on this spectrum "agents".

Workflow
  • Code defines steps and branches.
  • Tools run at specified steps.
  • AI interprets or generates.
More predefined decisions
Autonomous
  • Model chooses the next step.
  • Chooses tools from those allowed.
  • Adapts to what it finds.
More model-led decisions

Semi-autonomous sits between: AI directs most of the work, with human or code-based checkpoints.

This is the agency-control trade-off from Lecture 1, where agency = autonomy (decisions delegated to AI) and control = decisions retained by the person. Choose the balance for each part of the system.

Design decision

How to decide on autonomy

Prefer a workflow when
  • You can draw the decision tree.
  • Steps and choices are predictable.
  • AI is needed at specific steps.
Give more autonomy when
  • The next step depends on discoveries.
  • The path varies between runs.
  • Tools and actions are chosen on the fly.

In the instructors' experience, roughly 95% of enterprise AI use cases call for semi-autonomous systems.

Autonomy is a system design decision

"I was charged twice, and my order hasn't arrived."

Agent-directedOne agent chooses among Billing, Orders and Delivery tools.
Router-basedA router sends to Billing / Orders / Delivery, each with its own tools. Defined routes + human handoff for exceptions.

Both should produce one coherent customer response. Domain experience tells you where to delegate and where to keep control.

Part 3 · Product evals

How do we know the design works?

Domain experience helps design the first version. Evaluation tests whether it produces the outcomes users need. Three questions: what should happen? What happened? What needs to change?

Model evalsCan the model perform the task?Compare models on defined tests.
Product evalsDoes our application work for our users?Test our data, tools, rules and customer behaviour.

A strong model score doesn't prove the whole product works.

Evaluation continues throughout the life of the application

Known evils (evals): routing correctness

We know this requirement in advance: each question must reach the right team. Route by the underlying problem; suspected unauthorized activity takes priority.

Unknown evils (evals)

End-to-end failures & LLM judges

A question can reach the right department and still get a poor response. Routing accuracy asked "did it pick the right team?"; now ask "did QuickCart handle the request correctly?" by reviewing complete interactions for failure patterns.

Finding and evaluating unknown failures

6 steps

You be the annotator

Apply the rubric

Escalate if: customer angry or frustrated · swearing or abusive · fraud, security, billing dispute or compromised account · already tried and failed · asks for a human · unusual enough for a person. Otherwise handle directly. Did the assistant make the right call?

First three are the lecture's cases; the last two are my examples.

While building the evalCompare reference and actual answers. Find the repeated failure. Write the criteria.
When the judge runsRead the new request and response. Apply the rubric. No reference answer required.

Other evals may still compare against a reference answer.

Judges can favour longer answers or vary between runs. Use clear labels and reasons; monitor their cost and mistakes.

LLM judge practiceWhat it means
Use clear labelsCorrect / Incorrect with defined criteria, not a vague 1–10 score
Match the model to the judgmentA simple escalation check may need a less capable model than a complex technical review
Give a focused rubricSupply the context and criteria a domain expert would need
Validate against human labelsTest unseen cases; inspect disagreements and bias toward longer answers

Why a separate judge (not a self-check)?

Self-check in the same call"Write the reply, then verify that you handled escalation correctly."Can repeat the same mistaken interpretation and favour its own answer.
Separate review call"Read this request and reply. Apply the escalation rubric."A focused review task, like asking a second reviewer.

The assistant's job is to understand, use tools, follow policy and reply; it may miss a handoff along the way. The judge reads the finished interaction and checks one criterion. A separate call can use the same model and can still be biased, so validate its verdicts against human judgments.

Lens

Instructions tell the AI what to do; evaluations tell us whether it did it.

How it helps you improve: keep the same rubric while the application changes. Run version A on saved cases, change the prompt or model for version B, run the same cases, then ask: did missed handoffs fall without unnecessary ones rising?

Choose offline tests, online checks or both based on the stakes and when failures must be caught.

Input and output guardrails

Guardrails enforce limits during use. Input guardrails check requests before the model runs; output guardrails check the response before it reaches the user. Checks can be code, classifiers or LLM judges, and the application enforces what happens next: block, redact, pause/retry, or hand off.

Where does it get caught?

Pick a scenario

Scenarios are my examples; each maps to a guardrail named on the slides.

Input

  • Jailbreak detectionFlag attempts to bypass safety rules
  • Prompt-injection checkFlag instructions hidden in documents
  • Content moderationBlock disallowed harmful requests
  • Personal-data maskingRedact card numbers before a model call
  • Input size limitReject oversized uploads
  • File validationAllow only approved file types

Data & access

  • Customer ownershipOnly retrieve this customer's orders
  • Role permissionsLimit payroll access to authorized staff
  • Secret protectionKeep API keys out of model context
  • File sandboxRestrict access to approved folders
  • Network allowlistConnect only to approved domains
  • Export restrictionsBlock private records sent externally

Tools & actions

  • Tool allowlistDisable tools the agent doesn't need
  • Argument validationReject invalid order IDs or amounts
  • Read-only accessAllow SELECT, deny database writes
  • Transaction limitsRequire approval above a refund limit
  • Human approvalPause before sending a customer email
  • Duplicate preventionPrevent the same payment running twice

Output & execution

  • Output schemaReject responses missing required fields
  • Sensitive-data filterBlock passwords in the final reply
  • Grounding checkFlag claims unsupported by sources
  • Business-rule checkReject discounts outside policy
  • Step and time limitsStop a run that loops or times out
  • Failure fallbackHand off after repeated tool failures
Post-deployment evaluation

Production failures may not throw errors

Nothing crashes when an agent gives a wrong answer. Watch user signals instead.

User signalWhat to investigate
Thumbs down or repeated questionsWas the answer wrong, unclear or incomplete?
User abandons the conversationDid we fail the task or make it too slow?
Unusual turn count or latencyWas the agent stuck, misrouted or overusing tools?

Sample these interactions and run your evals to see whether something failed.

Evals are both an art and a science

Error analysis (science)What failures do we see in the interactions?
Domain expertise (art)What must we check, even if it hasn't failed yet?

Example: a support expert adds a privacy check, "Did the agent reveal another customer's order details?" Test for this risk even if it hasn't appeared in your samples.

Evaluate the outcome your users need

Use domain knowledge to define success, test the whole application including its decisions and actions, and turn failures into fixes, better test cases and repeatable checks.
